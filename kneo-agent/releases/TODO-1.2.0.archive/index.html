    Release Checklist — kneo-agent v1.2.0¶

    Tracks the next minor release after v1.1.1 (tagged 2026-05-03).

    State at the time this file was written: - pyproject.toml version: 1.1.1 - Latest tag: v1.1.1 - CHANGELOG.md [Unreleased]: empty - Uncommitted: docs/README.md rewrite + new docs/README-dev.md (mirrors the top-level README split done in 1.1.1)

    A minor bump (1.1.1 → 1.2.0) requires at least one user-facing Added/Changed entry. If nothing in Phase 1 lands, this should ship as 1.1.2 instead.

    What kneo-agent is. A Python library / SDK — pip install kneo-agent, import kneo_agent. Users build their own application around it (a script, a worker, a FastAPI handler, a Lambda, a notebook). The SDK does not ship a daemon, an HTTP server, a CLI entry point, container images, deployment manifests, or an ops runtime. Anything in this checklist that sounds like "deploy kneo-agent" really means "make it easy for the user's application to integrate kneo-agent." Service-container concerns belong in a separate downstream product (see Out of scope below).

    Target audience: small / medium enterprise users, open-source developers, on-premise / self-hosted deployments, and enterprise data-source / service integration via tools and MCP. Prioritization rubric for everything below:

    • SME wins: production reliability, cost control, observability, drop-in defaults, predictable upgrades.
    • OSS-developer wins: clear extension points, low-friction contribution flow, stable public surface, runnable recipes.
    • On-prem wins: works fully air-gapped (no required egress), local / self-hosted LLM support, configurable provider endpoints (base_url), self-hosted observability backends, plays cleanly with whatever container / orchestration the user already has, no telemetry phone-home, reproducible installs.
    • Enterprise integration wins: agents reach internal data sources (SQL, object stores, file shares, search indices) and internal services (REST/gRPC, queues, ticketing/CRM/ERP) via tools and MCP, with credentials plumbed through a documented secret-loading pattern rather than embedded in prompts or tool args.
    • Deprioritize features that only pay off at large-enterprise scale (SSO/RBAC/audit at the SDK layer), single-team niches, anything that hard-codes SaaS-only assumptions, or anything that turns the SDK into a service runtime.

    What v1.1.1 already gives us (do not redo)¶

    Audit on 2026-05-04 confirmed these are already in the codebase. Phase 1 focuses on new work; touch these only to document or extend.

    • Middleware framework. AgentMiddleware Protocol + four hooks (wrap_run, wrap_stream, wrap_model_call, wrap_tool_call), BaseAgentMiddleware, and composable dispatch in kneo_agent/core/middleware.py:82-206. OpenTelemetryMiddleware ships in kneo_agent/observability/tracing.py:52-95.
    • record_arguments / record_results flags on OpenTelemetryMiddleware (tracing.py:84-85) — partial redaction story already exists; RedactionMiddleware should build on it, not replace it.
    • base_url / endpoint override path for OpenAI-compatible servers via the openai_client parameter on OpenAIAgentsImpl (providers/openai_agents/impl.py:50). LangChain wraps any BaseChatModel so the same path works there. Capability is real; the gap is documentation + first-class factory exposure.
    • No phone-home. Code audit found no analytics, update checks, or metrics egress. Only urllib.request.urlopen use is in kneo_agent/mcp/client.py:23-25 for the MCP HTTP/SSE transports (intentional, not telemetry). [telemetry] extra ships only opentelemetry-api; the SDK does not impose an exporter.
    • RunResult.metadata["usage"] field exists (core/types.py:98) and OpenTelemetryMiddleware._set_usage_attributes() reads input_tokens/output_tokens (with prompt_tokens/ completion_tokens aliases) from it (tracing.py:219-234). Shape is implicit. Other documented keys in the API reference today: metadata["stopped_by_max_iterations"] and metadata["plan"] (Plan-Act strategy). The new formal usage spec should join those, not replace them.
    • MCP HTTP / SSE transports with custom headers (mcp/client.py:70-106, MCPServerConfig.http(headers=...) / .sse(headers=...)). Bearer/JWT auth already works; TLS / mTLS / custom-CA still missing.
    • Issue + PR templates and Dependabot config are present: .github/ISSUE_TEMPLATE/{bug_report,feature_request}.yml, .github/pull_request_template.md, .github/dependabot.yml.
    • Python 3.13 in CI matrix (.github/workflows/ci.yml:55); only the pyproject.toml classifier line is missing.

    Phase 1 — Decide scope¶

    Pick which to commit to before starting implementation. Each item is tagged with primary audience win and current state from the audit (NEW / PARTIAL → finish / DOC-ONLY). Everything below is a library deliverable: Python API, importable extension point, runnable example, or doc.

    Release blockers for v1.2.0 — these must land or the release slips:

    • First-class local-LLM API (Tier B base_url=).
    • Standardized RunResult.metadata["usage"] schema (Tier B).
    • Regenerated API reference at v1.2.0 (Phase 4).
    • Public API compatibility snapshot test (Phase 1.5).
    • Sensitive-data redaction regression tests (Phase 1.5), gated on the credential-plumbing item landing.

    Anything else may slip to a later release if not already implemented and tested by the freeze date — keep the bar at "ship something useful, not everything in Tier A/B/C/D."

    Per-feature design checkpoint — apply before writing code, not after. For every new public primitive in any Tier-A/B/C item, decide explicitly: 1. Does it belong in top-level kneo_agent.__all__, in a subpackage export only, or as experimental / internal? 2. Document that decision in docs/api_stability.md (the new file from Tier C) at the same time the code lands, not in a follow-up. 3. The API reference section that owns the new primitive must be updated in the same PR (Phase 4 has the regenerate step, but per-PR signature drift is what makes regeneration painful).

    Tier A — High-leverage, mostly net-new¶

    • [ ] Production-ready middleware bundle (SME + on-prem) — NEW. RetryMiddleware, RateLimitMiddleware, TokenBudgetMiddleware, RedactionMiddleware, all built on the existing AgentMiddleware framework. The redaction one should compose with the existing record_arguments/record_results flags on OpenTelemetryMiddleware rather than duplicate them. Acceptance criteria:
    • Export from a stable public module (e.g. kneo_agent.middleware.*) with documented import paths added to __all__.
    • Document ordering rules for static (constructor-time) vs per-run (RunConfig.middlewares) middlewares; include an example showing deterministic ordering when the same class is registered both ways.
    • Test composition: RedactionMiddleware paired with OpenTelemetryMiddleware(record_arguments=False, record_results=False) produces spans with no leaked args/results, asserted directly from a MemoryExporter.
    • Each middleware ships an examples/cookbook/ snippet exercising its primary use case.
    • [ ] Enterprise data-source tool patterns *(enterprise integration
    • on-prem) — NEW. Runnable cookbook recipes for the common shapes — these are snippets the user pastes into their own application*, not pre-built tool packages:
    • SQL (PostgreSQL / MySQL / SQL Server) — read-only query tool with parameter binding, schema-introspection helper, and a pagination-aware fetch.
    • Object store (MinIO / on-prem S3-compatible) — list / get / put with endpoint_url override.
    • REST / HTTP service — typed request tool over httpx, with a per-host auth header injector.
    • Search index (Elasticsearch / OpenSearch) — query tool.
    • File share — already covered by the MCP filesystem server (example 12_mcp_stdio_filesystem.py); cross-link from the cookbook. Goal is patterns and recipes, not a vendored client zoo — keep third-party deps out of the core install.
    • [ ] Credential / secret plumbing for tools + MCP (enterprise integration + on-prem) — NEW. Small SecretProvider protocol (or documented env-var + secret-file pattern) so credentials reach tool handlers and MCP transports without appearing in prompts, tool args, or trace spans. Pair with the new RedactionMiddleware.
    • [ ] Workflow reliability primitives (SME + on-prem) — PARTIAL → finish. Graph-shape orchestration already exists: the API reference documents WorkflowBuilder.add_edge(..., condition=...) and WorkflowEdge.condition, so conditional branching is in v1.1.1 — it just isn't surfaced as a first-class pattern.
    • Add a retry-on-failure workflow step / wrapper (the genuinely missing piece) with backoff knobs.
    • Decide whether the existing WorkflowBuilder is the public graph builder. If yes, document it as such (rename in docs, cross-link from each *Builder page); do not introduce a parallel WorkflowGraphBuilder that duplicates the API.
    • Add cookbook + unit tests showing conditional branching via WorkflowEdge.condition. Only introduce a new dedicated "conditional step" type if it materially improves ergonomics over add_edge(..., condition=...); otherwise stick with documentation + examples.
    • [ ] Cookbook examples (SME + OSS + on-prem + enterprise integration) — NEW directory, examples/cookbook/, with integration recipes (small Python scripts users adapt into their own application code): customer-support agent; RAG over an internal SQL warehouse; document-extraction pipeline reading/writing to MinIO; internal-API triage agent (REST tool + retry); worked cost-cap example; fully-local stack against a user-run Ollama; air-gapped pip install; end-to-end "enterprise inside the firewall" walkthrough combining local LLM + internal MCP server + SQL tool + object-store tool + secret provider. The smoke test in tests/integration/test_examples.py should pick these up.

    Tier B — Finish what's already half-done¶

    • [ ] First-class local-LLM API + example (on-prem) — PARTIAL → finish. Currently the API reference exposes openai_client (a pre-built AsyncOpenAI) on build_agent, build_sync_agent, BridgeAgentFactory.for_openai, and NativeRuntimeFactory.for_openai, but no direct base_url= parameter. Surface base_url= (or endpoint=) directly on each of those entry points so users don't have to pre-construct the client. Add examples/cookbook/local_ollama.py exercising it (assumes the user is running Ollama themselves; the SDK does not start one). Document the supported local servers (Ollama / vLLM / llama.cpp / LocalAI) in README and a new docs/local_llm_guide.md. Update the API reference entries for all four entry points to include the new parameter.
    • [ ] Standardized usage / cost metadata (SME + on-prem) — PARTIAL → finish. The current API reference only describes RunResult.metadata as "strategy-specific extras," so the contract is implicit. Write a formal RunResult.metadata["usage"] schema spec in core/types.py docstring and as a new section in the API reference under RunResult, with the matching OpenTelemetry attribute mapping cross-referenced from the observability section. Then audit every runtime — Bridge / Native / Adapter for OpenAI, LangChain, Google ADK — to confirm they all populate the documented keys. Add a unit test per runtime asserting the shape.
    • [ ] MCP TLS / mTLS / custom-CA support *(enterprise integration
    • on-prem) — PARTIAL → finish. The current API reference documents MCPServerConfig.http() / .sse() with headers and timeout only — no TLS knobs. Extend both factories (mcp/client.py:70-106) with verify, ca_bundle, client_cert, client_key parameters. The current urllib.request.urlopen path needs an SSLContext. Update the API reference MCP section* to show the new signatures, plus expand docs/mcp_guide.md with a corporate-TLS / mTLS recipe.
    • [ ] Self-hosted observability walkthrough (SME + on-prem) — PARTIAL → finish. New docs/self_hosted_observability.md showing end-to-end wiring of the existing [telemetry] extra to a user-run OTLP collector → (Jaeger / Grafana Tempo / SigNoz). The SDK exports spans; the user runs the backend.
    • [ ] OSS scaffolding gaps (OSS) — PARTIAL → finish. Add CODE_OF_CONDUCT.md (Contributor Covenant 2.1), SECURITY.md (private-disclosure email + supported-version table), and enable GitHub Discussions; link both from README. Issue/PR templates and Dependabot are already present — leave them alone.

    Tier C — Small lift, high signal¶

    • [ ] Air-gapped install + no-phone-home doc (on-prem) — DOC-ONLY. Code audit confirmed there is no egress; we just need to say so. Add a "No phone-home" section to README and a new docs/offline_install.md with the pip download --dest wheelhouse/ ... → pip install --no-index --find-links wheelhouse/ ... flow.
    • [ ] MCP server catalog from config (enterprise integration + on-prem) — NEW. Document the recipe for declaring a list of MCPServerConfig entries from YAML/JSON in the user's own application bootstrap (operators want to declare internal MCP endpoints per environment without code changes); ship a tested examples/cookbook/ snippet exercising it. Recipe-only — no first-party config-loader API in this release.
    • [ ] Public API stability tier doc (SME + OSS + on-prem) — DOC-ONLY. New docs/api_stability.md (or a section in CONTRIBUTING.md) declaring: what is public surface (everything in kneo_agent.__all__), the deprecation policy (one minor of DeprecationWarning before removal), and what counts as experimental (mark in docstring + CHANGELOG entry).
    • [ ] Upgrade guide — docs/upgrading_to_1.2.md (SME + on-prem) — DOC-ONLY. Short "should I upgrade?" walkthrough covering: new defaults, the local-LLM base_url= parameter, the formal RunResult.metadata["usage"] shape, any middleware behavior changes, MCP TLS knobs, and any deprecations. Even a mostly-additive minor benefits from a one-page upgrade narrative — most readers won't diff CHANGELOG entries.
    • [ ] Python 3.13 classifier (SME + OSS) — TRIVIAL. Add Programming Language :: Python :: 3.13 to pyproject.toml classifiers (line 19). CI already runs on 3.13.

    Tier D — Audit gaps to fold in cheaply¶

    • [ ] Streaming-support contract clarity (SME + OSS) — Bridge
    • OpenAI Native + Google ADK Adapter all stream; LangChain Adapter conditional on astream. Document each runtime's streaming status and make supports_streaming() authoritative; pair with a unit test that asserts StreamingNotSupportedError is raised explicitly rather than silently falling back. Doc + small test, cheap.
    • [ ] Sync API guidance — README/API-doc consistency (SME + OSS) — DOC-ONLY. README and docs/README.md don't yet repeat this.     Phase 1.5 — Release-quality test gates¶

    Contract tests and CI guards that protect v1.2.0 from accidental regressions. None of these are features; they're nets. Land them alongside the Phase 1 work, not as an afterthought.

    • [ ] Public API compatibility snapshot test. Add tests/unit/test_public_api_snapshot.py that snapshots kneo_agent.__all__ (and ideally each subpackage's __all__) against a checked-in expected list. Failures force the author to either (a) revert the unintentional change, or (b) update the snapshot and add CHANGELOG + API-reference entries in the same PR.
    • [ ] Middleware ordering contract tests. Add unit tests asserting the documented ordering: static-constructor middleware runs first, per-run (RunConfig.middlewares) middleware appended deeper. Cover short-circuiting (a middleware returning early prevents inner ones from running), exception propagation (an inner middleware raising is observable to outer wrappers), and the same rules under Agent.stream() not just Agent.run(). Lock the contract before the new middleware bundle (Tier A) lands.
    • [ ] Sensitive-data redaction regression tests. Run a fixture matrix of representative secrets — API keys, bearer tokens, database connection strings (postgres://...), S3 access-key pairs, JWT-shaped strings, MCP Authorization headers — through an agent with RedactionMiddleware + OpenTelemetryMiddleware + SecretProvider. Assert none of the secret values appear in: middleware logs, OTel span attributes, exception messages, or any serialized tool-call trace. Block the credential-plumbing item from shipping until this passes.
    • [ ] Minimal-core install (no extras) CI job. Add a CI matrix cell that installs kneo-agent with no extras and runs a smoke import asserting that Agent, AgentBuilder, ToolRegistry, the workflow primitives, MCP types, and the middleware-bundle classes import without pulling openai-agents / langchain / google-adk / opentelemetry-*. Belt-and-braces against accidental top-level imports of optional deps.
    • [ ] Deprecation-warning behavior tests. For every name marked deprecated under the new stability policy (Tier C), add a unit test asserting that (a) using it emits DeprecationWarning, and (b) it still produces the documented runtime behavior in v1.2.0 (one-minor grace period). Cross-link the deprecation in CHANGELOG.md and docs/api_stability.md.

    Out of scope — not the SDK's job¶

    kneo-agent is a Python library. The items below are valid concerns, but they belong to whatever process / container / orchestrator the user wraps the SDK in — i.e., a separate downstream product (e.g. a kneo-agent-server or an ops-tooling project). Documented here so future scope reviews don't relitigate them.

    • Shipping a Dockerfile / container image / deployment manifests for "the SDK". The SDK doesn't run; it's imported. Containers, Helm charts, K8s YAML, systemd units, and docker-compose.yml files for a deployed service all live in the user's application repo (or a separate deployment product). The cookbook may show a user-side compose snippet that runs Ollama + an OTLP collector for a local dev loop, but that's user infrastructure, not an SDK artifact.
    • An ops CLI or daemon entry point. [project.scripts] was intentionally removed in 1.1.1 (the old kneo-test / python -m kneo_agent smoke runner). Re-introducing a kneo-agent serve command — or any long-running entry point — is out of scope.
    • Declarative whole-agent config from a file (YAML/TOML for the full provider / model / tools / middlewares / skills / MCP servers graph). Belongs in a deployment / orchestration product. The MCP-catalog cookbook recipe in Tier C is the only declarative slice scoped into the SDK; everything else stays Python-API.
    • HTTP service wrapper, readiness / liveness endpoints, K8s probes. Building a FastAPI / gRPC service around an Agent is application code. The SDK does not provide /health, /ready, or any HTTP surface, and 1.2.0 will not change that.
    • SSO / RBAC / multi-tenant audit at the SDK layer. Belongs in the surrounding deployment layer.
    • Process-level concerns — log shipping, secret-store integration with Vault / SSM / KMS as a service, queue workers, autoscalers. The SDK exposes hooks (middleware, SecretProvider) that an application can use to plug into these; it doesn't implement them.
