    Kneo Agent Platform 0.1.1 release notes¶

    Date: 2026-05-14

    Summary¶

    Kneo Agent Platform 0.1.1 is a docs-and-packaging release on top of v0.1.0. The runtime code under kneo_serv/ is unchanged from v0.1.0; every substantive change in this cut is documentation, build tooling, or release plumbing. One observable behavior change ships: the installed CLI binary is renamed from kneo-serv to kneo so it matches what the Typer app prints in --help output.

    For per-line detail, see CHANGELOG.md § 0.1.1.

    Breaking change¶

    The installed console-script is now kneo (was kneo-serv). The pyproject.toml [project.scripts] entry installs kneo and the Dockerfile CMD is ["kneo", "service", "serve", …]. The Typer app has always identified itself as kneo in --help, so this aligns the binary name with what users see on screen.

    Unchanged: the Python distribution name (kneo-serv), the Python extras (kneo-serv[deploy] / [postgres] / [telemetry] / [dev]), the module package (import kneo_serv), and every pip install kneo-serv reference.

    Migration: any script, CI pipeline, alias, Dockerfile-from-image, or shell history that invokes kneo-serv <subcommand> needs to become kneo <subcommand>. The subcommand surface — config, spec, run, runs, human, service — is unchanged. Common substitutions:

    # before
kneo-serv config show
kneo-serv spec validate examples/research_agent.yaml
kneo-serv run examples/research_agent.yaml --input "hello"
kneo-serv runs get <run_id>
kneo-serv service serve --host 127.0.0.1 --port 8000

# after
kneo config show
kneo spec validate examples/research_agent.yaml
kneo run examples/research_agent.yaml --input "hello"
kneo runs get <run_id>
kneo service serve --host 127.0.0.1 --port 8000

    The CLI app's --help output, the generated CLI reference at docs/user/cli_reference.md, and the generated OpenAPI at openapi.json are all unchanged — only the installed binary name moves.

    Documentation¶

    This release ships a substantial expansion of operator-facing docs and introduces a versioned reading-path artifact set.

    New operator docs under docs/user/¶

    • tls_and_proxy.md — reverse-proxy topology, TLS termination, bind-address guidance, trusted-proxy headers, and worked nginx / Caddy / AWS ALB snippets.
    • security_hardening.md — pre-launch hardening checklist covering API-key issuance/rotation, role/scope selection, spec-bundle signing, TLS, container/host posture, and audit-trail protection; enumerates the capabilities explicitly out of scope for 0.1.x.
    • backup_and_recovery.md — consolidated PostgreSQL and SQLite backup procedures, off-site rotation, verified restore, the full rollback procedure (absorbed from the prior inline upgrade.md content), a data-only restore pattern for fresh PostgreSQL volumes, and a disaster-recovery scenario matrix.
    • observability.md — structured-log field reference, log-aggregation wiring (ELK / Loki / cloud-managed), OpenTelemetry exporter setup, and the production alerting baseline.
    • incident_response.md — on-call triage tree mapping /healthz and /readyz outcomes to the right troubleshooting-runbook section, including a per-check failure matrix sourced from kneo_serv/service/routes_health.py.

    Combined reading paths under docs/pub/¶

    Three rolled-up handouts compiled from the canonical docs/user/*.md sources, each shipped as both markdown and PDF with cover + TOC + per-chapter page breaks (same layout as design_handout.pdf):

    • kneo_agent_platform_tutorial.md / kneo_agent_platform_tutorial.pdf — quickstart, custom-tool tutorial, PostgreSQL deployment tutorial, human-in-the-loop walkthrough. 26 pages.
    • kneo_agent_platform_reference.md / kneo_agent_platform_reference.pdf — CLI usage and command reference, HTTP API contract, environment variables, examples walkthrough, project configuration. 51 pages.
    • kneo_agent_platform_operation_guide.md / kneo_agent_platform_operation_guide.pdf — deployment shapes, TLS/proxy, hardening, observability, backup and recovery, upgrade, incident response, troubleshooting, deployment smoke. 43 pages.

    The individual files under docs/user/ remain the authoritative single-page versions. The combined documents are generated by docs/script/generate_combined_docs.py and rendered to PDF by docs/script/render_combined_handouts.py. CI gates both with --check.

    Doc reorganization¶

    Targeted cleanups since v0.1.0:

    • project_dot_kneo_addendum.md → project_config.md — the _addendum suffix suggested draft scaffolding; the file is the canonical reference for the .kneo/config.yaml schema.
    • docs/script/deployment_smoke.md → docs/user/deployment_smoke.md — it is an operator runbook for scripts/deployment_smoke.py, not build tooling; docs/script/ is now exclusively doc-build tooling source.
    • scripts/generate_reference_docs.py → docs/script/ — relocated alongside the other doc-render tooling.
    • TODO.md → docs/plan/TODO-0.1.0.md — every item in the 0.1.0 TODO is [x] complete, so the top-level scratchpad is archived per version.
    • Dated 2026-05-07 verification snapshots were trimmed out of deployment_smoke.md; the procedural value (a data-only PostgreSQL restore pattern) moved into backup_and_recovery.md as a third pattern.
    • Targeted deduplication of roles tables (security_hardening.md defers to service_api.md § Authentication for canonical scopes), OTel env vars (observability.md defers to environment.md), and the /readyz matrix (troubleshooting.md § 1.2 defers to incident_response.md).

    Build and release tooling¶

    • docs/script/generate_combined_docs.py — combined-document generator. Demotes each source's heading hierarchy by one level (code-block-aware), rewrites in-group cross-references to local anchors, and rewrites out-of-group user-doc references to ../user/<file>.md. Source files in docs/user/ are not modified. CI runs the script with --check and fails on drift.
    • docs/script/render_combined_handouts.py — combined-handout PDF renderer. Reuses the mermaid + puppeteer pipeline from render_design_pdf.py and the cover / TOC / page- number-resolution helpers from render_design_handout.py. Each chapter starts on a new page; TOC entries resolve to body page numbers via a two-pass render.
    • .github/workflows/ci.yml and .github/workflows/release.yml gained --check steps for both generators. The release gate at .github/workflows/release.yml continues to verify pyproject.toml version matches the pushed v* tag.

    Verification¶

    Local sanity gates run clean on the rename and the docs work:

    • python -m ruff check kneo_serv tests scripts docs/script — passed.
    • python -m ruff format --check kneo_serv tests scripts docs/script — passed.
    • python -m compileall -q kneo_serv tests scripts docs/script — passed.
    • python docs/script/generate_reference_docs.py --check — passed.
    • python docs/script/generate_combined_docs.py --check — passed.
    • mkdocs build --strict — passed.
    • python -m pytest -q --no-cov -m "not load and not failure_injection and not provider_integration and not postgres_integration" — 181 passed, 5 deselected (the opt-in markers; their previous results remain valid as no kneo_serv/ runtime code changed since v0.1.0).
    • Reinstalled the package in a fresh editable install: which kneo resolves; which kneo-serv is empty; kneo --help prints Usage: kneo ….
    • Verified zero stale kneo-serv CLI or kneo-serv API process strings across all four committed PDFs (design_handout.pdf and the three combined-doc handouts) and across the rendered mermaid SVG assets.

    Operational assumptions¶

    Carried over from v0.1.0 unchanged:

    • PostgreSQL integration tests remain opt-in with KNEO_SERV_RUN_POSTGRES_INTEGRATION=true and KNEO_SERV_DATABASE_URL.
    • Real-provider integration tests remain opt-in with KNEO_SERV_RUN_PROVIDER_INTEGRATION=true and the provider's API key.
    • deploy/production.env and deploy/staging.env are local-only and gitignored; only the .example templates ship in source artifacts.
    • The Docker image installs the kneo-serv[deploy] extra so PostgreSQL and SDK telemetry dependencies are present out of the box.
    • No public artifacts were withdrawn for 0.1.1. Users on v0.1.0 can stay there indefinitely; the upgrade is opt-in and reversible (pip install the prior version + restore a pre-upgrade backup if needed). See upgrade.md for the procedure.
